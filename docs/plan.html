GoldenEye 007 on iOS

Research findings and staged plan. Public repo, unsigned IPAs via GitHub Actions, sideloaded with SideStore. No Mac.

STAGE 0 RESULT

Answered on device, iOS 26.6.1. The hardcoded memory model cannot work on iOS.

__PAGEZERO size: 0x100000000

CART    @ 0x10000000   vm_allocate FAIL kr=1 (invalid address)
                       mmap MAP_FIXED FAIL errno=12 (ENOMEM)
DRAM V1 @ 0x70000000   FAIL, same
DRAM K0 @ 0x80000000   FAIL, same

Shrinking __PAGEZERO is not an escape. That build fails to load at all under LiveContainer with segment '__TEXT' vm address out of order, because LiveContainer dlopens the guest executable and dyld enforces segment ordering on that path. The approach is unsupported on iOS and incompatible with how you actually run apps, so it is dropped.

Consequence: Stage 1 now definitely includes rebasing the port's memory model. See below.

What we are starting from

Your ROM is GoldenEye 007 (USA, rev 0), internal name GOLDENEYE, cart code NGEE, sha1 abe01e4aeb033b6c0836819f549c791b26cfde83. That is byte-identical to the US target in both goldeneye_src/ge007.u.sha1 and the PC port's expected ge007.ntsc-final.z64. Every tool in this ecosystem will accept it unchanged.

The one thing that decides this project

The GoldenEye PC port hardcodes three mappings below the 4 GB line, and arm64 iOS walls that entire region off.

port/src/dram.c maps N64 working RAM twice, at 0x70000000 (an s32-safe view) and 0x80000000 (a KSEG0 mirror), because the decompiled game code does arithmetic like *(u16 *)(word | 0x80000000) on 32-bit values. port/src/romdata.c maps the cart image at 0x10000000. All three use MAP_FIXED, and the build forces -fno-pie, -no-pie and -Wl,-Ttext-segment=0x20000000 to keep symbols in that range.

On arm64 Mach-O, __PAGEZERO is 4 GB by default, so everything under 0x100000000 is unmapped and unmappable. iOS also requires PIE. The port's own romdata.c:164 already names 0x100000000 as a boundary, so the author is aware of it.

Whether a sideloaded app can shrink __PAGEZERO and claim those addresses is not documented anywhere I can check from Linux. It is the difference between a normal port and a rewrite of how 166k lines of game code address memory. So we answer it first, on your actual phone, before writing anything else.

The staged plan

0

Probe the address space days

A ~170-line UIKit app, no SDL, no engine. It asks the kernel for each of the three regions with vm_allocate(VM_FLAGS_FIXED) and with mmap(MAP_FIXED), writes a byte to the first and last page to prove the memory is actually usable rather than merely reserved, prints __PAGEZERO's real size from the Mach-O header, and renders a verdict on screen.

Suite B then tests the fix: reserve one 4 GB-aligned window wherever the kernel will give one, commit the cart and DRAM sub-ranges inside it, alias the KSEG0 view onto the same pages with vm_remap, and assert that W + (phys | 0x80000000) really does land on the mirrored bytes.

This doubles as the proof of the whole CI recipe: CMake with the Xcode generator, CODE_SIGNING_ALLOWED=NO, and Payload/-into-zip IPA packaging. Whatever the verdict, the pipeline is then known-good.

Done. Suite A returned NOT USABLE for all three regions. The probe now carries a suite B that tests the proposed replacement on device before we commit to it.

1

Fork the port, get it compiling for arm64

Fork goldeneye-pc-port into this repo and make it build with Clang for iOS. Two known obstacles, both independent of the Stage 0 answer:

  • Clang instead of GCC. The build forces GCC for -fplan9-extensions, which the decomp's #define inherits struct idiom in src/bondtypes.h relies on. Clang's -fms-extensions covers part of the same ground; the gap has to be measured, not guessed.
  • Memory model, now confirmed required. Replace the three fixed mappings with a single 4 GB-aligned window W, so an N64 address v becomes W + v. The game's | 0x80000000 arithmetic keeps working untouched in the low 32 bits, and pointers stored back into u32 fields still round-trip. port/src/libultra.c:796 already collects the two bases into one array, which is the seam to widen; the scattered inline *(u16 *)(word | 0x80000000) dereferences are the work, and they need a counting pass before the effort can be estimated honestly. Perfect Dark proves the engine family does not need the trick: its platform.h treats __aarch64__ as first-class with PLATFORM_64BIT.

Exit: an arm64 iOS binary links, even if it renders nothing.

2

Rendering backend

The port has only gfx_opengl.cpp, written against desktop GL 3.3 core, which does not exist on iOS. The seam is gfx_rendering_api.h, plus gfx_window_manager_api.h for the window.

Take GLES 3.0 through SDL2's existing iOS backend rather than writing Metal. SDL2 already supports iOS, sm64coopdx-ios does exactly this (SDL_GL_CONTEXT_PROFILE_ES, version 3.0 on iOS), and Perfect Dark's shader generator already emits GLES-aware GLSL with precision mediump float and texture() vs texture2D() switching. Metal is a later optimization, not a first step.

Budget real time for shader compatibility. Both reference ports hit this and fixed it in dedicated commits; GLSL-ES rejects things desktop GL accepts.

Exit: the gun-barrel intro renders on the phone.

3

Touch controls and the app shell

Follow sm64coopdx-ios and draw the controls with the game's own renderer rather than overlaying UIKit views. It keeps the layout in sync with the framebuffer, scales across iPhone and iPad, and avoids a second view hierarchy. Buttons map onto the same N64 button bitmask the engine already uses.

A dual-stick FPS needs more thought here than a platformer did. GoldenEye's native scheme is unusual even on N64, so expect to design rather than copy: left stick to move, right drag to aim, with aim-assist worth considering given a touchscreen.

The app shell needs landscape lock, UIRequiresFullScreen, hidden status bar, safe-area insets so buttons clear the Dynamic Island, and CADisableMinimumFrameDurationOnPhone for ProMotion. Two SDL quirks are already documented: disable accelerometer-as-joystick, and iPadOS turns gamepad presses into synthetic keyboard events.

4

ROM loading, then audio

UIFileSharingEnabled and LSSupportsOpeningDocumentsInPlace expose the app's Documents folder in the Files app. You drop GoldenEye.z64 in, the app hashes it against the known US sha1, and refuses anything else. Optionally a UIDocumentPickerViewController import button.

Audio is last because it is entirely absent from the GoldenEye port today on every platform: port/src/audio.c is 70 lines of stub. This is new work, not porting work, and the reason the port is not yet playable anywhere.

If the rebase turns out to be too wide

Stage 0 came back negative, so this is live. The fallback is to build the iOS platform layer against perfect_dark_pc first, which is already arm64-clean, already playable, and shares fast3d and the same port/ architecture. You would get a working N64 FPS on your phone early, and the renderer backend, touch controls and IPA pipeline all carry over to GoldenEye once its memory model is rebased. Nothing built would be wasted.

Ground rules

  • No ROM, and nothing extracted from one, in the repo or in any artifact. .gitignore covers it.
  • No GitHub Releases. CI artifacts only, 14-day retention. The repo is public for free macOS runner minutes, not to distribute builds.
  • code/ stays gitignored read-only reference. Not submodules.
  • macOS runner jobs carry timeout-minutes and narrow path triggers.

Research across goldeneye_src, goldeneye-pc-port, GoldenRecomp, perfect_dark, perfect_dark_pc, sm64ex-ios, sm64coopdx-ios and SCInsta. Claims about the memory model and build flags were verified directly against the source, not taken from summaries.
